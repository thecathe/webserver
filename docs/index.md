# ddm: the deployment manager

!!! info "Status (2026-10-18): the server's config is built; installing it is next"
    `ddm` validates the [site spec](usage/spec.md), builds and publishes every site, generates the Caddyfile, and
    serves the whole set locally with a shared toolbar (`bin/ddm preview`; see [operations](usage/operations.md)).
    The droplet's NixOS config (M5) exists and passes a VM test. Nothing is live yet: installing it needs your
    secrets ([to-dos](tasks.md)), then the daemon (M6) and the reinstall of the droplet (M7). The old droplet still
    runs the previous hand-made setup, which will be wiped.

## What it is for

One repo (this one) is the **only** place with GitHub secrets or CI. Everything else is declared in a spec:

- **Sites**: which of your repos to pull, which reusable **workflow** builds each one (forester, odoc, mkdocs, an
  OCaml "notebook" built from `.ml` files, …), and which **host and path** each output is mounted at.
- **The server itself**: ddm pulls this repo and rebuilds the droplet's NixOS configuration from it, including
  updating ddm itself.

Adding a new project means adding a spec entry, with no per-repo Actions, keys or secrets. That also makes it cheap
to stand up **project-specific sites** that a team can use, whether hosting material directly or redirecting to it.

Two more goals run through the design:

- **Consistent styling** across every site and every kind of generated output (forest, mkdocs, odoc, …), from one
  shared palette and set of styles rather than per-site copies.
- **Cross-linking between subdomains**: any site can link to any other by name (`site://<name>/<path>`), resolved
  per view, so links survive hosts and paths changing.
